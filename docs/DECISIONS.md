# Offline decision prototype

`go run ./cmd/rules -mode decision` demonstrates a fast recommendation checked by the native engine and applies it in an offline simulation. It does not operate the game client.

Construct `rules.DecisionInput` from a confirmed complete public `View`, a unique match identifier, phase `turn`, the active player, all hand instance IDs in confirmed left-to-right `HandOrder`, explicitly supplied candidate actions and a deadline made with `time.Now().Add(budget)`. Do not deserialize the deadline: it must retain Go's monotonic clock. The caller owns observation freshness, hand order, the candidate list and the final check against the current game state. Both decision paths choose a legal action for the leftmost card. If that card has no legal supplied action, they return no decision; with an empty hand, a legal pass can be chosen.

Create one `DecisionService` per match session and call `Close` on exit; its dedicated goroutine waits for semantic updates throughout the session. `Start` supplies a copied public view and candidates, cancels obsolete analysis and queues the latest update. Repeating the same state and deadline does not restart work or replay a consumed action. Keep the original deadline for an observation; a different deadline with otherwise identical state is rejected. A changed match, phase, view, revision or candidates invalidates the old proposal. `Poll` returns a completed proposal only for the same input, after another legality check. If no proposal is ready, use `Fast`; do not wait for analysis. `Close` cancels work and waits for the goroutine to exit. Go schedules the goroutine; this is not a dedicated operating-system thread.

Call `Invalidate` immediately when an observation becomes unusable or action eligibility is lost, even if no replacement input exists. It cancels current work and clears queued inputs and results without stopping the session worker. The caller must serialize state updates and invalidations in observation order, and still check the current observation before execution.

The policy does not optimize card choice or mulligans. Opponent hand and deck identities are never provided to the policy; counts do not reveal their contents. Both paths use a public-state projection for legality, supported only for the six `native-v1` cards. The projection cannot establish observation authenticity, and native-v1 does not reproduce all client rules or Bearly Balanced behavior. The existing tracker requires a full-information initial state and is not a live partial-state estimator. Neither the prototype nor the demo provides the observed candidates or executes input.

The collector's observation report supplies a timestamp, window/process identity, geometry and a screenshot reference, but does not establish the game phase, active player, cards, candidate legality or turn deadline. A report reference by itself cannot satisfy `DecisionInput`; future integration requires independently validated perception and phase authorization. The action transport's freshness and single-use checks do not certify game rules.
